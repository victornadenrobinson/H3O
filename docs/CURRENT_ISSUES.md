## 2. Physics: open questions

**P1. Insertion vs crystal mixing are consistent, and the dilute limit is strongly negative.** Insertion gives the dilute chemical potential (mu_H - G_H ~ -0.5 eV, about -1 kT, after the pressure correction). The crystal value is the average over 27 added H (x = 0.25 H/O, e.g. +76 meV at 500 GPa 6000 K, +141 at 5500 K). A linear (regular-solution) fit through the corrected n = 1, 2, 4 averages extrapolates to +55 (5500 K), -83 (6000 K) and +275 (400 GPa 5000 K) at n = 27, against +141, +76 and +192 direct: agreement within ~100-150 meV, which is the noise of a 7x extrapolation. So mu_H rises steeply with concentration (~20 meV per added H in 108 O at constant P). The fixed-V pressure rise explains only ~25% of the raw insertion slope.
- Consequence: H is soluble in superionic fcc H2O up to roughly **x ~ 0.07-0.15 H/O** (differential mu_H = G_H(pure)) at 400-500 GPa, 5000-6000 K. A positive per-added-H average at x = 0.25 does NOT mean "insoluble" (summarize label fixed; the report generator, not in this repo, still says "positive = H not soluble").
- Needed: points at x ~ 0.05-0.15 to locate the solubility limit (insertion n = 8, 16, or crystal runs `hper` 2.074 / 2.111 / 2.148 with 108 O; the empty `fcc_400GPa_6500K_h2.0xxxxo` dirs were meant for this), and long runs (insertion n=1 has +-30-45 meV and 30-85 meV drift at 2 ps).

**Ideal-solution reference (page 8 of the report, paper text).** Identical mobile protons, no -kT ln x singularity: mu_id = kT ln(N_H) + const, N_H = (2 + a) N_O, so d mu_id / da = kT / (2 + a) (differential), kT/4 for the per-added-H AVERAGE that the insertion and crystal rows are. Lattice-gas variant with M sites per O: S_id = -k N_O [c' ln(c'/M) + (M - c') ln(1 - c'/M)], c' = 2 + x, gives a differential slope kT M / (c' (M - c')) = kT M / (2 (M - 2)) at x -> 0 (M = 3: 3 kT / 2; M -> inf: kT / 2). The TDI assumes no lattice (all configurational entropy is in the integral); M only changes the guide line. Measured slopes (18-52 meV per added H in 108 O = 2-5.6 eV per unit H/O) are far above any ideal value: the concentration dependence is non-ideal (plus the uncorrected cell pressure rise). State the finite mu_H(x -> 0) explicitly in the paper.

## 2c. Performance (measured 2026-10-28, A100 40 GB, GRACE ft_m2, 251 atoms)
Single process: 0.16 s per GRACE call (stage-0 free NVT, 3200 steps in 8.6 min). Lambda processes share one GPU by time-slicing (no MPS): 8 processes ~750 ms/step each (insertion: 2 calls/step) = ~10.7 steps/s total; 2 processes ~360 ms/step each = ~5.6 steps/s. nvidia-smi 100% busy, 4.5 GB per TensorFlow context (8 fit in 40 GB; the 9th and 10th died of OOM, now handled by the memory-aware NPAR and the OOM retry in young_tdi_par.sh). CPU not the bottleneck (node 86% idle). Candidates: NVIDIA MPS; one batched process for all lambda replicas (one GRACE call per step, 2500+ atoms); LAMMPS + GRACE. To do in a separate session, benchmarked against the current engine (same node files, same results).
Monitor (young_tdi_par.sh, every MONEVERY=30 s, merged 2026-10-28 from two sessions): every lambda process (both engines) rewrites `<tag>_node<k>_progress.json` every 30 s (steps done / total / speed over the last 5 min; an ASE observer that only reads the step counter and the clock). `tdi/eta.py` adds them up: one WHOLE JOB line every 30 s (all lambda values of the launch incl. those waiting for a slot; per-lambda engine: event simulation with the time-slicing table scaled to the speed measured now; batched engine: lock step), per-lambda lines + GPU + live integral every 8th time. Stage 0 and prep print a progress line every minute (also during the equilibration). The `== launch` markers in the node logs are kept.
**Faster engine, opt-in, NOT yet the default (2026-10-28): `ENGINE=batch`** (tdi/batched.py, run_real.py --batch-nodes): all lambda values in one process, one batched GRACE call per MD step (insertion: host + host-with-ghost in the same call). Each lambda value still runs the unchanged run_node (same Langevin, RNG streams, files, restarts) in a thread; only the model calls are gathered. Validated in the sandbox: toy model node files (npy, state, thermo csv, traj) BIT-IDENTICAL to the per-lambda engine for insert, fcc, pure H, liquid (with HOT) and for restarts mixing the two engines; toy T0 bookkeeping unchanged (exact); random GRACE-2L model on CPU: batched vs single call 3e-16 eV/atom, node series 1e-13 eV after 120 steps. A self-check (batched vs single call on the start structure) runs before any MD and refuses to start if they differ. tensorpotential's exported `compute` treats its input as ONE structure but returns per-atom energies and per-bond pair forces, so disjoint structures are packed into one graph and split back (energy, forces, stress all recovered). CPU cost: matscipy neighbour list ~45 ms per 250-H structure at 6 A (900 neighbours/atom), holds the GIL: built in a pool of worker processes. GPU out of memory: the call is split in halves automatically (BATCHMAX=<atoms> to start smaller). **Benchmark on Young (2026-10-28, insH 251 atoms, docs/PERFORMANCE.md): the batched engine is SLOWER, 7.1 steps/s vs 10.9 (8 processes, time-slicing) and 11.9 with MPS (+10%).** The GPU kernels are the limit (46 ms of GPU per structure with 8 processes vs ~58 ms per structure in one big batched call); batching only removes CPU/latency overhead, which 8 processes already hide. Keep ENGINE=batch opt-in (correct, not useful here); use MPS. The dense tensorpotential engine (GRACE_MODE=uniform, 0.6.1 on Young, ft_m2 supports it) gave NO gain in the real engine (336 vs 307 ms/step) and needs 6.6 instead of 4.6 GB per process (8 processes OOM): not used. Process sweep (PERFORMANCE.md): the GPU saturates at 4 lambda processes (insH 11.5 steps/s, pure H 22.7; ~23 GRACE calls/s for 250 atoms); 8 processes are not faster, so use NPAR=4 (default: half the memory, no OOM). Remaining levers: fewer MD steps (heavier H mass + larger dt, adaptive length per lambda: need a decision).
Do not `git pull` while a launcher started with `bash` (interactive) is running: bash reads scripts as it runs them. young_tdi_par.sh / young_insert_checks.sh now end in `main "$@"; exit $?` on one line (safe from now on); the *.sbatch wrappers run with plain `bash` are not (under sbatch Slurm runs a spooled copy, safe). ## 4. Known limitations, not fixed (judgement calls)
- `17_eos_md.build()`: H on random bond midpoints: exact composition but locally 0-4 H per O, H-H down to d_OO/2 in the start frame.
- Restarted nodes reseed the RNG from the seed (not a bias, not a bit-exact continuation).
- A restart records one extra sample: the fresh ASE dynamics calls its observers at step 0, so the restart configuration (already the last sample of the previous chunk) is stored twice. One duplicate per restart, no bias; the chunk count `len(series) // n_per` would only be off after n_per (500) restarts. Pre-existing, unchanged (both engines do it).
- 5-block errors: +-35% relative uncertainty; +-1 SEM covers ~63% (4 dof). Errors of short (<= 2 ps) runs are optimistic; use the drift column.
- Finite size: ln N! Stirling terms (~ -6 meV per added H at 6000 K for 108 O / 250 H); 96-atom liquid cells; only one H finite-size pair (400 GPa 6500 K, N 250 vs 500: equal within 5 meV/atom).
- Toy LJ blows up at the smallest lambda (bare r^-12): toy-only, but any potential with a stiff core needs dt checks at lambda < 1e-6.
- The report generator is `mlp_pipeline/tdi/report.py` (branch claude/eloquent-ramanujan-2tjx2p, merged here): figures + tables from summarize.py CSVs; check its labels and fits against this list.
